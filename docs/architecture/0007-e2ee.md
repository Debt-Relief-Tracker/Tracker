# ADR 0007: End-to-end encrypted mode (`E2EE=true`) on Hologram

## Status

Proposed. Phase 0 (feasibility) is partly done; see "Spike findings".

## Context

ADR 0005 encrypts sensitive columns with a server-held key (Cloak). Anyone
who controls the server -- or the key it holds -- can still read everything.
The owner wants an `E2EE=true` mode where the server stores only ciphertext
and never holds a key, so a database dump, backup or hosting provider learns
nothing about the data.

That has a hard consequence: the server can no longer run the payoff engine
or render screens from data, so both must run in the browser. Rather than
rewrite the engine in JavaScript, the browser code stays Elixir via
[Hologram](https://hologram.page), which compiles Elixir to JS.

## Decision

- **Switch:** `E2EE` env var, read once in `config/runtime.exs`. Unset keeps
  plaintext storage. No server-side-key mode.
- **UI:** Hologram pages/components for the whole app in both modes; LiveView
  is retired for app screens. Phoenix stays for routing, OIDC and assets.
- **Engine:** pure Elixir with no Ecto, `Decimal`, `Date` or floats -- the
  `DebtReliefTracker.Engine.*` modules (integer cents, basis points, day
  counts). The Decimal engine (`Debts.Calculations`, `Planning`) remains the
  reference the new engine is tested against until the UI is ported.
- **Persistence:** a `Storage` behaviour with `Storage.Plain` (today's
  contexts) and `Storage.Vault` (ciphertext), behind identical Hologram
  commands.
- **JS:** facade files only (WebCrypto, Argon2, WebAuthn PRF, Chart.js,
  download). No application logic in JS.
- **Keys:** a random 32-byte vault key encrypts one JSON document with
  AES-256-GCM. Each unlock method (Argon2id passphrase, WebAuthn-PRF passkey,
  256-bit recovery key) wraps that vault key, so adding or changing a method
  never re-encrypts the data. AADs bind blobs to workspace and revision.
- **Sync:** compare-and-swap on `rev` (`UPDATE ... WHERE rev = base_rev`);
  on conflict the client decrypts, merges (payments/activity: union by id;
  debts/settings: last-writer-wins on `updatedAt`, tombstones) and retries.
- **Login** stays OIDC and is separate from unlocking. Hosted E2EE requires
  OIDC. Sharing by email is off in E2EE v1.
- **Auto-logged installments:** client-side catch-up on open in both modes,
  with deterministic payment ids (`debt_id:due_date`) so devices converge.
- **Migration of existing data:** on first load with `E2EE=true`, an owner
  with plaintext rows gets a forced setup wizard (the browser must create the
  key; the server cannot). The browser builds and uploads the vault,
  re-downloads it and verifies it decrypts and matches. Only then does a
  separate delete command remove the plaintext rows, and that step requires
  explicit owner confirmation and a prior export. Until a user completes the
  wizard, their plaintext stays on the server. Going back to plaintext is
  unsupported.
- **Rule for agents and contributors:** never log, parse or decrypt vault
  data server-side.

## Spike findings (Hologram 0.12.4, pinned)

- Compiles alongside the app on Phoenix 1.8 / Elixir 1.19 / OTP 28.
- Hologram has no ports of `Decimal`, `Date` or `:calendar`; only
  Elixir/Erlang functions it has ported can run in the browser. Hence the
  integer-only engine and `Engine.Days`.
- Its first-load HTML contains two inline `<script>` tags carrying
  per-request values (CSRF token, instance id, page params) with no nonce
  support. A strict `script-src 'self'` CSP needs a plug that adds a
  per-request nonce to them (hashes cannot work), to be re-verified on each
  Hologram upgrade. Its interpreter also uses `new Function` for
  `JS.eval/exec`; the app must not use those, or CSP needs `unsafe-eval`.
- Hologram 0.12 uses a WebSocket in addition to HTTP; CSP needs
  `connect-src 'self'`.
- Not yet verified: passkey PRF on real devices/authenticators, the
  locked-shell first render. (AES-GCM/Argon2/PRF-in-Chromium, CSP and bundle
  size are verified; see "Crypto facade findings".)

## Crypto facade findings (Phase 5)

Code: `assets/js/crypto_facade.mjs` (plain ES module) behind
`DebtReliefTracker.Crypto`. No hand-rolled primitives: WebCrypto for
AES-256-GCM, HKDF-SHA256, SHA-256 and randomness; `hash-wasm` (npm, bundled
locally, no CDN) for Argon2id. All facade calls take and return strings
(base64url without padding; fields of a structured result joined with `.`).

- **Envelope** (document ciphertext and key wraps): `v1.<iv>.<ct>`, both
  parts base64url; `iv` is 12 random bytes drawn fresh inside every
  encryption (no caller-supplied IV, no counter), `ct` is AES-256-GCM
  ciphertext followed by the 16-byte tag. Parsing is strict (version,
  canonical base64url, IV length, minimum tag length); anything malformed is
  the same error as a failed tag check.
- **AAD**: document `"drt-vault-v1" 00 workspaceId 00 String(revision)`;
  wrap `"drt-wrap-v1" 00 workspaceId 00 wrapId 00 kind` (kind is
  passphrase|passkey|recovery). Ids may not be empty or contain NUL.
- **KEKs**: passphrase = Argon2id(NFKC(passphrase), 16-byte salt) with params
  passed explicitly and stored with each wrap (start: 64 MiB, 3 passes, 1
  lane, 32 bytes); stored params above 1 GiB / 20 passes / 16 lanes, or
  below Argon2's own minimums, are rejected (`bad_params`). Passkey = WebAuthn
  PRF with salt SHA-256("drt-prf-salt-v1"), output through HKDF-SHA256
  (empty salt, info "drt-kek-v1"). Recovery = 256 random bits shown as 13
  dash-separated groups of 4 RFC 4648 base32 chars; parsing ignores case,
  spaces and dashes, and rejects wrong length, characters and non-zero pad
  bits; KEK = same HKDF over the 32 bytes.
- **Errors**: one `decrypt_failed` code for every decrypt/unwrap failure (wrong
  key, wrong AAD, tampering, malformed envelope). Other codes are about
  caller input or the passkey ceremony (`passkey_unsupported`,
  `passkey_cancelled`, `passkey_failed`) and do not depend on secrets. The
  Hologram surface returns `"ok:<value>"` / `"err:<code>"` strings and never
  throws or echoes messages. Nothing logs; nothing touches storage, cookies
  or URLs; derived keys exist only as locals within a call.
- **CSP**: Argon2's WebAssembly needs `'wasm-unsafe-eval'` in `script-src`.
  Verified in Chromium 131 with `script-src 'self' 'wasm-unsafe-eval'`: the
  facade, self test and Argon2id all run. With plain `script-src 'self'`
  WebAssembly compilation is refused (`CompileError`) and Argon2 cannot run.
  The facade itself needs no `'unsafe-eval'` (a test also bans `eval` and
  `new Function` in its source). Remember Hologram's own `JS.eval/exec` need
  `'unsafe-eval'` and the app must not use them.
- **Argon2id timing** (64 MiB, 3 passes, 1 lane, headless Chromium 131, this
  dev machine, 7 runs after load): 357-408 ms in the page; about 0.5 s
  click-to-done for the whole Hologram flow (derive, wrap, unwrap, encrypt,
  decrypt). Phones will be several times slower; the params are stored per
  wrap so they can be raised later. hash-wasm runs lanes sequentially, so
  `parallelism > 1` gives no speed-up and `1` is the right choice.
- **Bundle size** (dev build): the facade plus hash-wasm is 38 KB minified
  standalone. Hologram's `CounterPage` bundle is 20,844 B and the test-only
  `CryptoPage` (facade + hash-wasm + a small page) is 84,766 B (about 21 KB
  gzipped), so roughly +64 KB unminified. `DashboardPage` is 934,293 B and is
  unchanged until it uses `DebtReliefTracker.Crypto` (nothing does yet).
- **Passkey PRF**: Chromium 131's CDP virtual authenticator supports PRF
  (`hasPrf: true`); create (with PRF) and a later get yield the same KEK.
  Without `hasPrf` the facade returns `passkey_unsupported`. Not verified:
  real platform authenticators/security keys, Safari/Firefox, and which
  authenticators return PRF output only on `get` (the immediate-get fallback
  is implemented but the virtual authenticator may not exercise it).
- **Test vectors**: AES-256-GCM McGrew-Viega cases 13-16 (16 has AAD);
  HKDF-SHA256 RFC 5869 cases 1 and 3; SHA-256 "abc"/empty; RFC 4648 base32.
  hash-wasm cannot express RFC 9106 5.3 (it has `secret` but no associated
  data), so that vector is checked against Node's independent OpenSSL
  Argon2id, which reproduces it, and hash-wasm is compared with that
  implementation on the same inputs without AD, and at 64 MiB / 3 / 1.
- **Decisions**: the recovery key carries no checksum (a typo yields
  `decrypt_failed` on unwrap); the Elixir facade is only usable from
  Hologram actions (JS interop is a server no-op, giving `:not_in_browser`).

## Consequences

- The integer engine rounds interest to a cent when posted, so simulation
  totals can differ from the Decimal engine by under a cent per debt-month.
  `test/debt_relief_tracker/engine/parity_test.exs` pins orders, minimums
  and month counts exactly and bounds interest drift, against fixtures
  generated from the Decimal engine
  (`test/support/fixtures/generate_engine_scenarios.exs`).
- A user who loses every unlock method loses their data; backups are
  ciphertext-only. This goes in the Terms.
- Large rewrite of `DashboardLive` (~2000 lines) and `AdminLive`; the
  existing LiveView tests are the behavioural spec to port.
- ADR 0005's Cloak encryption stays for plaintext mode and is bypassed in
  E2EE mode.
