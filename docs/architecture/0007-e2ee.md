# ADR 0007: End-to-end encrypted mode (`E2EE=true`) on Hologram

## Status

Accepted -- **go** (2026-10-31), implementation in progress (docs/roadmap.md
Phase 10). Open items before E2EE can ship are listed under "Still open".

## Context

ADR 0005 encrypts sensitive columns with a server-held key (Cloak). Anyone
who controls the server -- or the key it holds -- can still read everything.
The owner wants an `E2EE=true` mode where the server stores only ciphertext
and never holds a key, so a database dump, backup or hosting provider learns
nothing about the data.

That has a hard consequence: the server can no longer run the payoff engine
or render screens from data, so both must run in the browser. Rather than
rewrite the engine in JavaScript, the browser code stays Elixir via
[Hologram](https://hologram.page), which compiles Elixir to JS.

## Decision

- **Switch:** `E2EE` env var, read once in `config/runtime.exs`. Unset keeps
  plaintext storage. No server-side-key mode.
- **UI:** Hologram pages/components for the whole app in both modes; LiveView
  is retired for app screens. Phoenix stays for routing, OIDC and assets.
- **Engine:** pure Elixir with no Ecto, `Decimal`, `Date` or floats -- the
  `DebtReliefTracker.Engine.*` modules (integer cents, basis points, day
  counts). The Decimal engine (`Debts.Calculations`, `Planning`) remains the
  reference the new engine is tested against until the UI is ported.
- **Persistence:** a `Storage` behaviour with `Storage.Plain` (today's
  contexts) and `Storage.Vault` (ciphertext), behind identical Hologram
  commands.
- **JS:** facade files only (WebCrypto, Argon2, WebAuthn PRF, Chart.js,
  download). No application logic in JS.
- **Keys:** a random 32-byte vault key encrypts one JSON document with
  AES-256-GCM. Each unlock method (Argon2id passphrase, WebAuthn-PRF passkey,
  256-bit recovery key) wraps that vault key, so adding or changing a method
  never re-encrypts the data. AADs bind blobs to workspace and revision.
- **Sync:** compare-and-swap on `rev` (`UPDATE ... WHERE rev = base_rev`);
  on conflict the client decrypts, merges (payments/activity: union by id;
  debts/settings: last-writer-wins on `updatedAt`, tombstones) and retries.
- **Login** stays OIDC and is separate from unlocking. Hosted E2EE requires
  OIDC. Sharing by email is off in E2EE v1.
- **Auto-logged installments:** client-side catch-up on open in both modes,
  with deterministic payment ids (`debt_id:due_date`) so devices converge.
- **Migration of existing data:** on first load with `E2EE=true`, an owner
  with plaintext rows gets a forced setup wizard (the browser must create the
  key; the server cannot). The browser builds and uploads the vault,
  re-downloads it and verifies it decrypts and matches. Only then does a
  separate delete command remove the plaintext rows, and that step requires
  explicit owner confirmation and a prior export. Until a user completes the
  wizard, their plaintext stays on the server. Going back to plaintext is
  unsupported.
- **Rule for agents and contributors:** never log, parse or decrypt vault
  data server-side.

## Spike findings (Hologram 0.12.4, pinned)

- Compiles alongside the app on Phoenix 1.8 / Elixir 1.19 / OTP 28.
- Hologram has no ports of `Decimal`, `Date` or `:calendar`; only
  Elixir/Erlang functions it has ported can run in the browser. Hence the
  integer-only engine and `Engine.Days`.
- Its first-load HTML contains two inline `<script>` tags carrying
  per-request values (CSRF token, instance id, page params) with no nonce
  support. A strict `script-src 'self'` CSP needs a plug that adds a
  per-request nonce to them (hashes cannot work), to be re-verified on each
  Hologram upgrade. Its interpreter uses `new Function` for
  *every* server payload, not just `JS.eval/exec`, so the CSP needs
  `'unsafe-eval'` regardless (see "Content-Security-Policy").
- Hologram 0.12 uses a WebSocket in addition to HTTP; CSP needs
  `connect-src 'self'`.
- Not yet verified: passkey PRF on real devices/authenticators, the
  locked-shell first render. (AES-GCM/Argon2/PRF-in-Chromium, CSP and bundle
  size are verified; see "Crypto facade findings".)

## Crypto facade findings (Phase 5)

Code: `assets/js/crypto_facade.mjs` (plain ES module) behind
`DebtReliefTracker.Crypto`. No hand-rolled primitives: WebCrypto for
AES-256-GCM, HKDF-SHA256, SHA-256 and randomness; `hash-wasm` (npm, bundled
locally, no CDN) for Argon2id. The string-key functions (base64url
without padding; fields of a structured result joined with `.`) remain as named
exports for the Node known-answer tests and JS-side migration code; **what
Hologram can reach is only the opaque-handle API** ("Client vault flows",
below).

- **Envelope** (document ciphertext and key wraps): `v1.<iv>.<ct>`, both
  parts base64url; `iv` is 12 random bytes drawn fresh inside every
  encryption (no caller-supplied IV, no counter), `ct` is AES-256-GCM
  ciphertext followed by the 16-byte tag. Parsing is strict (version,
  canonical base64url, IV length, minimum tag length); anything malformed is
  the same error as a failed tag check.
- **AAD**: document `"drt-vault-v1" 00 workspaceId 00 String(revision)`;
  wrap `"drt-wrap-v1" 00 workspaceId 00 wrapId 00 kind` (kind is
  passphrase|passkey|recovery). Ids may not be empty or contain NUL.
- **KEKs**: passphrase = Argon2id(NFKC(passphrase), 16-byte salt) with params
  passed explicitly and stored with each wrap (start: 64 MiB, 3 passes, 1
  lane, 32 bytes). Params policy: `deriveNewPassphraseKek` (every wrap the
  app writes, new or re-wrap) enforces a floor of 64 MiB, 3 passes and a
  16-byte salt; `derivePassphraseKek` (unwrap) honours the stored params and
  only rejects absurd ones (above 256 MiB / 10 passes / 4 lanes, or below
  Argon2's own minimums; `bad_params`). No floor on unwrap because a
  malicious server lowering stored params can only make unwrap fail, and the
  passphrase never leaves the browser; a floor on create means the app can
  never write weak params. Passkey = WebAuthn
  PRF with salt SHA-256("drt-prf-salt-v1"), output through HKDF-SHA256
  (empty salt, info "drt-kek-v1"). Recovery = 256 random bits shown as 14
  dash-separated groups of 4 RFC 4648 base32 chars: 52 chars of key plus a
  4-char checksum (first 20 bits of SHA-256("drt-recovery-check-v1" || key
  bytes)). Parsing ignores case, spaces and dashes and requires exactly 56
  chars, valid characters, zero pad bits and a matching checksum, else
  `bad_recovery_key`, so the UI can tell a typo from a wrong key
  (`decrypt_failed`). KEK = HKDF over the 32 key bytes (checksum excluded).
  No 52-char form is accepted (nothing was deployed with it).
- **Errors**: one `decrypt_failed` code for every decrypt/unwrap failure (wrong
  key, wrong AAD, tampering, malformed envelope). Other codes are about
  caller input or the passkey ceremony (`passkey_unsupported`,
  `passkey_cancelled`, `passkey_failed`) and do not depend on secrets. The
  Hologram surface returns `"ok:<value>"` / `"err:<code>"` strings and never
  throws or echoes messages. Nothing logs; nothing touches storage, cookies
  or URLs; derived keys exist only as locals within a call.
- **CSP**: Argon2's WebAssembly needs `'wasm-unsafe-eval'` in `script-src`.
  Verified in Chromium 131 with `script-src 'self' 'wasm-unsafe-eval'`: the
  facade, self test and Argon2id all run. With plain `script-src 'self'`
  WebAssembly compilation is refused (`CompileError`) and Argon2 cannot run.
  The facade itself needs no `'unsafe-eval'` (a test also bans `eval` and
  `new Function` in its source). Remember Hologram's own `JS.eval/exec` need
  `'unsafe-eval'` and the app must not use them.
- **Argon2id timing** (64 MiB, 3 passes, 1 lane, headless Chromium 131, this
  dev machine, 7 runs after load): 357-408 ms in the page; about 0.5 s
  click-to-done for the whole Hologram flow (derive, wrap, unwrap, encrypt,
  decrypt). Phones will be several times slower; the params are stored per
  wrap so they can be raised later. hash-wasm runs lanes sequentially, so
  `parallelism > 1` gives no speed-up and `1` is the right choice.
- **Bundle size** (dev build): the facade plus hash-wasm is 38 KB minified
  standalone. Hologram's `CounterPage` bundle is 20,844 B and the test-only
  `CryptoPage` (facade + hash-wasm + a small page) is 84,766 B (about 21 KB
  gzipped), so roughly +64 KB unminified. `DashboardPage` is 934,293 B and is
  unchanged until it uses `DebtReliefTracker.Crypto` (nothing does yet).
- **Passkey PRF**: Chromium 131's CDP virtual authenticator supports PRF
  (`hasPrf: true`); create (with PRF) and a later get yield the same KEK.
  Without `hasPrf` the facade returns `passkey_unsupported`. Not verified:
  real platform authenticators/security keys, Safari/Firefox, and which
  authenticators return PRF output only on `get` (the immediate-get fallback
  is implemented but the virtual authenticator may not exercise it).
- **Test vectors**: AES-256-GCM McGrew-Viega cases 13-16 (16 has AAD);
  HKDF-SHA256 RFC 5869 cases 1 and 3; SHA-256 "abc"/empty; RFC 4648 base32.
  hash-wasm cannot express RFC 9106 5.3 (it has `secret` but no associated
  data), so that vector is checked against Node's independent OpenSSL
  Argon2id, which reproduces it, and hash-wasm is compared with that
  implementation on the same inputs without AD, and at 64 MiB / 3 / 1.
- `__testOnlyEncryptWithIv` (deterministic IV) exists only for known-answer
  tests and the self test; it is not on the default (Hologram) export.
- **Decisions**: the Elixir facade is only usable from
  Hologram actions (JS interop is a server no-op, giving `:not_in_browser`).

## Server vault (Phase 6)

Code: `DebtReliefTracker.E2EE` (+ `.Vaults`, `.Vault`, `.KeyWrap`,
`.RateLimiter`), `Holo.Components.VaultGate`, `Storage.Vault`.

- **Schema** (migration `20261031120000_create_e2ee_vaults`, additive, no
  backfill, one directory for SQLite and Postgres):
  `e2ee_vaults(workspace_id PK/FK delete_all, rev int default 1, blob binary,
  format_version int default 1, inserted_at, updated_at)` and
  `e2ee_key_wraps(id PK, workspace_id FK delete_all + index, kind string,
  label, credential_id, kdf_params (JSON text), salt, wrapped_key, inserted_at)`
  with a unique index on `(workspace_id, credential_id)` (NULLs are distinct
  in both databases, so only passkey wraps are constrained). `kind`
  (passphrase|passkey|recovery) is validated in the changeset, not a DB enum.
  **Deviation from the plan table: there is no `iv` column** -- the IV lives
  inside the `wrapped_key` envelope (`v1.<iv>.<ct>`), as it does for the blob.
  The wrap `id` is client-chosen (a UUID) because the wrap AAD binds it.
- **Blind store:** the server checks only sizes (blob <= 5 MB; wrap fields
  <= 1 KiB; <= 20 wraps per workspace, of which <= 3 passphrase wraps: unlock
  runs Argon2id per passphrase wrap, and the client tries only the 3 oldest), the cheap shape of a wrap's fields,
  and kind-specific required fields. It never parses `blob`, `kdf_params` or
  the envelopes. Schema fields are `redact: true`, vault queries run with
  `log: false` (Ecto's debug log prints bound params), and the payload keys
  are in `:phoenix, :filter_parameters`.
- **Sync primitive:** `save(workspace, base_rev, blob)` is
  `UPDATE ... WHERE workspace_id = ? AND rev = ?` with `rev + 1`; zero rows
  returns `{:conflict, %{rev, blob}}`. Removing a wrap and adding one take a
  row lock on the vault (a no-op update) so the "never remove the last wrap"
  and count checks cannot race on Postgres.
- **Commands** (`VaultGate`: fetch, create, save, add/remove wrap, delete):
  workspace from `Holo.Context.workspace/1` only; the component carries the
  `Holo.Auth` middleware; each returns ONE `:vault_result` action to the page
  with plain maps/strings (errors are atoms such as `:conflict`,
  `:last_wrap`, `:too_large`, `:rate_limited`, `:invalid`).
- **Rate limit:** `E2EE.RateLimiter`, a per-workspace token bucket (capacity
  30, refill 1/s) whose state lives in ETS owned by a GenServer that does the
  arithmetic (so concurrent callers cannot double-spend). Per node, in memory,
  no dependency.
- **Switch and boot checks:** `E2EE` env (`true`/`1`/`yes`, case-insensitive)
  is read once in `config/runtime.exs` into `:e2ee`; `E2EE.enabled?/0` is the
  gate and `Storage.adapter/0` picks `Storage.Vault` (whose `load` and
  `apply_change` return `{:error, :e2ee_locked}`) unless `:storage` overrides.
  `Boot.run/0` first runs `E2EE.check_boot!/0`: E2EE on without OIDC is allowed
  only for `PHX_HOST` unset/localhost/127.0.0.1 (warning), otherwise boot
  raises; E2EE off while any vault row exists raises (never an empty app).
- **App behaviour in E2EE mode:** `/app` renders only a locked shell
  (`#e2ee-locked`, vault exists or not; no snapshot, no financial data);
  `/` (LiveView) redirects to `/app` because it would decrypt legacy
  plaintext with the server's Cloak key; `/export/*.csv` return 410; `/admin`
  is unchanged. Legacy plaintext rows stay in the database untouched until
  Phase 9 deletes them.
- **Not yet:** the vault status shown is `exists?` only; the client never
  receives a snapshot. Real Postgres was not run against the migration.

## Client vault flows (Phase 7) and save/sync loop (Phase 8)

Code: `assets/js/{crypto_facade,vault_store,vault_env}.mjs`,
`DebtReliefTracker.{Crypto,VaultEnv}`, `DebtReliefTracker.VaultClient.*` (pure:
`Strength`, `Delay`, `Recovery`, `SaveLoop`), `Holo.VaultFlow` (the state
machine), `Holo.Components.{VaultSetup,VaultUnlock,VaultMethods,VaultHome,VaultGate}`
and `Holo.DashboardPage` (E2EE branch). Browser tests:
`holo/e2ee_client_browser_test.exs`, `holo/e2ee_sync_browser_test.exs`.

### Final facade surface: opaque handles, raw keys never enter Elixir

The unlocked session (vault-key bytes plus a derived **non-extractable**
AES-GCM `CryptoKey`) lives in module-private JS memory. Elixir and Hologram state
hold only a random handle id (`"h" + 16 chars`), ciphertext envelopes, ids and
revisions. The default (Hologram) export contains *only*: `prfSupported`,
`selfTest`, `vaultNew`, `vaultLock`, `vaultLockAll`, `vaultActive`,
`vaultCanManage`, `vaultEncrypt`/`vaultDecrypt` (handle, workspace, revision),
`vaultWrapPassphrase`/`vaultWrapRecovery`/`vaultWrapPasskey` (handle in, wrap
fields out), `vaultUnlockPassphrase`/`Recovery`/`Passkey` (secret + the stored
wrap in, handle out), `deviceRemember`/`deviceHas`/`deviceUnlock`/`deviceForget`,
`seenCheck`/`seenRecord`, `localWipe`. A Node test asserts none of the string-key
functions is on that export. New code `locked` = unknown handle; every decrypt,
unwrap, tamper and wrong-AAD failure is still the single `decrypt_failed`.

The two values that must reach a human are a typed **passphrase** (in) and a new
**recovery key text** (out, shown once; the wizard drops it from component state
at hand-off). Multi-value results are joined with `|`.

Hologram detail learned the hard way: **an `await` inside an anonymous function
is not awaited by the interpreter**, so crypto calls are made from direct
recursion / `with`, never from closures passed to helpers.

### Phase machine and screens

    no_vault --wizard--> unlocked <--unlock-- locked
    unlocked --lock / idle / other tab locked--> locked   (saves first)
    any --start over (type DELETE)--> no_vault

* **Setup wizard** (`/app`, no vault): choose passkey (only when
  `prfSupported`) or passphrase (min 12 chars, simple length/class strength meter
  with a "too guessable" floor, confirmation, an offline-guessing warning,
  `deriveNewPassphraseKek`: 64 MiB / 3 / 16-byte salt, busy state during
  Argon2); generate the vault key and wrap it under the method AND a recovery
  key; show the recovery key once (14 groups, copy button) and require BOTH a
  checkbox and the final (checksum) group typed back; encrypt
  `VaultDoc.new()` (or the `initial_doc` prop, for Phase 9) as rev 1 and call
  `create_vault` with both wraps in one transaction. Other methods are added
  later in the methods modal.
* **Unlock** (vault exists): one section per enrolled kind from the server's
  `key_wraps`; passphrase uses the wrap's STORED salt/params (facade
  bounds-checks them); passkey = WebAuthn PRF `get`; recovery key tolerant of
  case/dashes, a checksum mismatch gets its own "does not look like a valid
  recovery key" message. Any wrong secret or tampered wrap/blob is ONE generic
  message. Client-side delay: free for 3 failures, then 1, 2, 4 ... capped 30 s
  (`VaultClient.Delay`, UI memory only).
  After unwrap the page fetches, checks rollback, decrypts, decodes, runs
  `Ledger.catch_up` (auto-logged installments; the result goes through the same
  dirty/save path) and shows `VaultDoc.view(doc)`.
* **Session**: Lock button; idle auto-lock (default 15 min, `config
  :debt_relief_tracker, :e2ee_idle_ms`; reset by pointer/key/touch/wheel
  activity); `BroadcastChannel("drt-vault:<workspace>")` carries only the words
  `locked`/`unlocked` (locking in one tab locks the others of the browser;
  unlocking only shows a hint in locked tabs because no secret is shared);
  `visibilitychange` to visible refetches (rev check + merge); a
  `beforeunload` handler warns while changes are unsaved. All of it is in
  `vault_env.mjs`, which reports to the page by `Hologram.dispatchAction(
  "vault_session_event", ...)`; no inline scripts. Locking clears `doc`,
  `snapshot`, `sync`, the modal and calls `vaultLock(handle)`. A lock with
  unsaved changes saves first; if that fails the vault stays unlocked, says so,
  and offers "Lock anyway and discard".
* **Unlock methods modal** (locked screen and unlocked page): list (kind,
  label, created), rename, add passphrase / passkey, regenerate recovery (the
  new key must be acknowledged; it replaces the old recovery wrap: add new, then
  remove old), remove (server refuses the last), change passphrase (verify the
  old one, wrap the same vault key under the new one, add new then remove old;
  the document is never re-encrypted), "Start over" (type DELETE; server wipe +
  `localWipe`; works while locked). Everything that changes a wrap needs a
  session that holds the vault key; a remembered-device session cannot.
  Server additions (no migration): `Vaults.rename_key_wrap/3`, `Vaults.create/3`
  takes a list of wraps (all or nothing), `Vaults.key_wraps/1`; `VaultGate`
  `:rename_key_wrap` and `create_vault %{wraps: [...]}`; wrap maps carry
  `inserted_at`.

### Remember this device (decision)

Opt-in checkbox at setup and unlock (and a button in the modal). The session's
non-extractable `CryptoKey` (encrypt/decrypt only) is put in IndexedDB under the
workspace id; scripts on the origin can use it but never read its bytes. A
remembered device:
* opens the vault automatically on page load (`/app` mount), without a method,
  as long as no "locked" marker exists (a brand-new browser session with no
  marker still auto-unlocks);
* after a **manual, idle or cross-tab lock** does NOT auto-reopen, not even on
  a fresh page load: those locks write a NON-SECRET per-workspace "locked"
  marker in IndexedDB (next to the rev/hash record). Page load skips the
  auto-unlock while it exists; the unlock screen offers one click, "Unlock this
  device", which clears it (as does any fresh method unlock) -- so a lock only
  costs a click, not a secret, and a reload cannot silently reopen the vault.
  "Forget this device" removes both the key and the marker. Anyone with the
  unlocked browser profile can open the vault; the UI says so at every opt-in;
* can read and save the document but cannot add/remove/rename methods (the
  session has no vault key): the UI says "unlock with a method first";
* is removed by "Forget this device" (and by start over).
The idle timer still runs for remembered sessions.

Recovery key clipboard: about 60 s after "Copy recovery key" the page
overwrites the clipboard with an empty string. Best effort only (browsers may
refuse without focus; errors are swallowed; clipboard-history tools may keep a
copy); the setup screen says so.

### Rollback detection

IndexedDB `seen[workspace] = {rev, SHA-256(blob)}`, written after every
successful fetch-and-decrypt and every successful save. On every fetch or
conflict reply: a lower `rev`, or the same `rev` with a different hash, blocks
with a warning (`#vault-rollback`) that needs an explicit acknowledgment
("I understand, continue") before the data is used; acknowledging records the new
state. First sight of a workspace on a device cannot detect anything (documented
limit: a device that never saw a newer state trusts the server).

### Save/sync state machine (`VaultClient.SaveLoop` + `VaultFlow`)

    edit    Ledger.apply_change(doc, change, ctx) -> snapshot = view(doc)
            -> dirty, seq+1, debounce 1 s (a later edit supersedes the timer)
    flush   encrypt (fresh IV, AAD revision = base_rev + 1) -> save_vault(base_rev)
    ok      base_rev = new rev; seen[...] updated; edits that arrived meanwhile
            keep it dirty and trigger another flush
    conflict  server returns {rev, blob}: rollback check, decrypt, Merge.merge(local,
              remote), base_rev = rev, retry with backoff 0.5 s .. 30 s
    error   (rate limit, vault gone, network): status offline, same backoff
    >6 retries  status failed, still dirty, "Retry save" button, unload warning stays on

`ctx`: `now`/`today` from the browser clock, `new_id` = `crypto.randomUUID()`,
`actor` = the signed-in user id. Status badge `#vault-sync-status[data-status]`:
idle, dirty, saving, saved, merged, offline, failed. A dirty change is never
dropped silently. The page action `:vault_apply_change %{change: ...}` is the
mechanism the feature components will use; until they do, a config-gated test
hook (`config :debt_relief_tracker, :e2ee_test_hook, true`; on in the test
environment's browser tests only) renders an add-debt form and pay/delete
buttons on the unlocked screen.

### Storage inventory (browser) and what the server holds

| Where | What |
|---|---|
| IndexedDB `drt-vault` / `device_keys` | the non-extractable CryptoKey, only with "remember this device" |
| IndexedDB `drt-vault` / `seen` | `{rev, SHA-256 of blob}` per workspace |
| `localStorage` | only the existing `phx:theme` preference |
| cookies | the Phoenix session cookie (no vault data) |
| sessionStorage, URLs, logs | nothing |
| JS memory | vault key bytes + document CryptoKey behind handles; decrypted `doc` in Hologram page state |
| Server DB | `e2ee_vaults.blob` (ciphertext), `e2ee_key_wraps` (wrapped keys, salts, kdf params, credential ids, labels) |

A browser test (`e2ee_sync_browser_test.exs`) runs a full session with unique
marker strings as debt name and passphrase and asserts that marker, passphrase
and recovery key appear in no row of any table (raw), no log line, no storage,
no cookie, no URL, and that IndexedDB contains only the records above.

### Verified / not verified

Verified in headless Chromium 131 (SQLite; Postgres via `scripts/pg_test.sh`):
all flows above including a CDP virtual authenticator with PRF. Not verified:
real platform authenticators, Safari, Firefox, mobile browsers (WebAuthn user
activation rules differ; the passkey step runs in an action chained ~40 ms
after the click), Argon2 timing on phones.

## Data path: the full dashboard in E2EE mode

In E2EE mode `/app` renders the SAME dashboard (header, sidebar, plan panel
with charts, retirement banner, modals, tutorial, footer) once the vault is
unlocked, driven by `snapshot = VaultDoc.view(doc)`. Behaviour, ids and error
messages match plaintext mode (`DualModeFlowsBrowserTest` runs one set of
flows in both modes).

**One abstraction for "apply a change"** (`Holo.DataPath`):

    DataPath.save(component, :save, %{changes: cs, notice: n},   # plaintext command
      changes: cs,                                               # E2EE ledger path
      ok: DataPath.synced(n, true),                              # reply actions
      error: DataPath.error(:save_failed, "debt_form_modal"))

* Plaintext: exactly `put_command(component, :save, params)`; the server
  applies the `Storage` change(s) and replies with an action.
* E2EE: the same component action puts ONE action on the page
  (`:vault_apply_request` -> `VaultFlow.apply_request/2`): all changes are
  applied in order through `VaultDoc.Ledger` (all-or-nothing) on the decrypted
  document, the snapshot is recomputed, the save loop is marked dirty, and the
  handler's single follow-up action is the **reply**: the component's `ok`
  action with the new `snapshot` (+ the client's `today`) in its params, or its
  `error` action with `%{error: error}` (`Storage.error` shapes identical to
  the server path, so the form/error rendering code is shared).
* The page puts `:e2ee` in the Hologram **context**; components declare
  `prop :e2ee, :boolean, from_context: :e2ee` (no prop drilling).
* The debounce timer of the save loop is a **JS timer**
  (`VaultEnv.flush_later/2` -> `vault_flush`), not a delayed `put_action`, so
  the one follow-up action stays free for the reply.
* Anything the server used to compute from plaintext is computed in the
  browser by the ledger from the snapshot with the client's `today`
  (`handle_due` cycle, `reconcile_balance` estimated balance, retirement
  member display names via `ctx.members`). Only account data stays server
  side: display/tracker name (`save_account` command), theme, tutorial flag,
  and the retirement member picker (`load_members`), activity-log actor names.
* Components mounted after unlock have no server `init/3`: they define
  `init/2` (today from `VaultEnv`; the plan panel starts from an empty plan and
  the page queues `:plan_inputs_changed` after unlock). Component state
  outlives lock/unlock (same `cid`), so that action also refreshes it.

**Divergences from plaintext mode (v1)**

* Sharing ("People") is hidden in settings with an explanation (sharing is off
  in E2EE mode); the workspace switcher is hidden (a second workspace is a
  second vault, opened by reloading).
* CSV export is built in the browser (`Holo.CsvExport`, `Holo.CsvDownload`,
  `assets/js/csv_download.mjs`; Blob + anchor click, CSP-safe). Same bytes as
  the server module for the same data (`csv_export_test.exs`: commas, quotes,
  CRLF/LF, unicode, formula prefixes). Both sides neutralise spreadsheet
  formula injection identically: a TEXT cell (name, note) starting with `=`,
  `+`, `-`, `@`, TAB or CR gets a leading `'`; numeric and date columns are
  untouched. Decimal scale: the client prints money and APR with
  2 decimals and the minimum-payment rate with 4; the server prints the stored
  `Decimal` as typed, so a value saved as `20` rather than `20.00` differs.
* Several changes of one action (log all balances) are atomic in E2EE mode
  (the server path applies them one by one and stops at the first error).

  totals can differ from the Decimal engine by under a cent per debt-month.

  and month counts exactly and bounds interest drift, against fixtures
  generated from the Decimal engine
  (`test/support/fixtures/generate_engine_scenarios.exs`).
- A user who loses every unlock method loses their data; backups are
  ciphertext-only. This goes in the Terms.
- Large rewrite of `DashboardLive` (~2000 lines, now deleted: the Hologram
  `/app` replaced it at the Phase 4 cutover) and `AdminLive`; the
  LiveView tests were the behavioural spec (`docs/cutover-test-coverage.md`).
- ADR 0005's Cloak encryption stays for plaintext mode and is bypassed in
  E2EE mode.

## Content-Security-Policy

Code: `DebtReliefTrackerWeb.Plugs.ContentSecurityPolicy` (endpoint, just before
`Hologram.Router`). Two policies, both sharing the `:csp` mode below:

**LiveView pages (`/admin`, `/auth/*`; `/` only redirects to `/app`)**: these share the origin -- and
so IndexedDB with the remembered vault key -- with `/app`, so an XSS there
would reach the key. They get a nonce-less policy (`liveview_policy/0`):

    default-src 'none'; script-src 'self' [<umami origin>];
    style-src 'self'; connect-src 'self' [<umami origin>];
    img-src 'self' data:; font-src 'self';
    object-src 'none'; base-uri 'none'; frame-ancestors 'none';
    form-action 'self' [<OIDC issuer origin>]

plus `Referrer-Policy: no-referrer` and `X-Content-Type-Options: nosniff`.
The theme boot script moved from an inline `<script>` in `root.html.heex` to
`assets/js/theme_boot.js` (esbuild entry, loaded synchronously in `<head>`,
no flash); a test fails if any inline `<script>` appears on `/` or `/admin`.
`connect-src 'self'` covers the same-origin LiveView WebSocket (verified in
Chromium; no `ws:`/`wss:` wildcard). No `style-src-attr` is needed: LiveView
and the UI only touch styles via the CSSOM. The Umami origin is added only
when analytics is configured. Not covered: `/dev/*`, LiveDashboard, `/api/*`
(Swagger UI needs inline scripts) and CSV exports.

**Hologram (`/app`, `/hologram/*`)** -- final policy (nonce is fresh per
request):

    default-src 'none';
    script-src 'self' 'nonce-<n>' 'unsafe-eval' 'wasm-unsafe-eval';
    style-src 'self'; style-src-attr 'unsafe-inline';
    connect-src 'self'; img-src 'self' data:; font-src 'self';
    object-src 'none'; base-uri 'none'; frame-ancestors 'none';
    form-action 'self' [<OIDC issuer origin>]

plus `Referrer-Policy: no-referrer`, `X-Content-Type-Options: nosniff`, and
`Cache-Control: no-store` on `/app` HTML and Hologram command responses.

- **Nonce**: 16 random bytes, base64url, per request. Hologram's two inline
  `<script>` blocks hold per-request values (hashes cannot work). A
  `register_before_send` callback runs after Hologram has substituted its
  placeholders and adds `nonce` to inline scripts only if their body starts
  with one of the two known Hologram prefixes (anything else is left bare, so
  injected markup cannot inherit the nonce; a warning is logged). External
  `<script src>` are untouched. Re-check the prefixes on each Hologram upgrade
  (a unit test goes through the real endpoint).
- **`'unsafe-eval'` is required** (evidence, not choice): Hologram 0.12's
  client runtime turns every server payload (SSE handshake, command replies,
  page mount data, deserializer) into values with
  `Interpreter.evaluateJavaScriptExpression` -> `new Function`
  (`assets/js/interpreter.mjs`, the only eval/`new Function` in the runtime).
  Without it, in real Chromium the SSE handshake loops forever and
  `sseConnected?` never becomes true. So the policy has *no inline-script
  escape hatch* (no `'unsafe-inline'`, no external hosts, nonce only), but it
  is not eval-free. Removing it needs an upstream/forked Hologram change.
  The app itself must not add eval sinks: a test fails if `JS.eval`,
  `JS.exec` or `~JS` appear in `lib/` (the app uses only `JS.call`).
- **`'wasm-unsafe-eval'`**: Argon2id WebAssembly (crypto facade). Redundant
  while `'unsafe-eval'` is present, kept so that dropping the latter does not
  silently break Argon2.
- **`connect-src 'self'`** covers fetch, the SSE EventSource and the
  WebSocket (Chromium matches `'self'` for same-host `ws:`; verified by the
  browser suite, where WebSocket and SSE both connect).
- **`style-src-attr 'unsafe-inline'`**: the UI sets inline `style` attributes
  (tutorial spotlight/card positions, computed widths). No `<style>` element
  is emitted (elements stay `style-src 'self'`); Chart.js sets styles via the
  CSSOM, which CSP does not restrict. Narrower than a blanket `'unsafe-inline'`.
- **`form-action`**: the logout POST is same-origin but is answered with a
  redirect to the IdP's `/v2/logout`; Chrome applies `form-action` to that
  redirect, so the configured OIDC issuer origin is added when OIDC is on.
  Not exercised against a real Auth0 tenant.
- **Hologram error overlay**: on an uncaught error or (dev) compile error the
  runtime injects a `<style>` element, which `style-src 'self'` blocks (overlay
  appears unstyled). Deliberately not allowed; it only shows when something is
  already broken. A browser test that triggers it fails on the violation.
- **`img-src data:`** for inline SVG/data-URI icons; **`frame-ancestors
  'none'`** forbids framing.
- **Rollout**: `config :debt_relief_tracker, :csp, mode: :enforce |
  :report_only | :off` (read per request). `:enforce` in test and prod;
  `:report_only` in dev (Phoenix.LiveReloader injects an iframe that
  `default-src 'none'` would block, and enforcing in dev was not verified).
  To roll out cautiously, set `:report_only` in prod first and watch the
  console, then `:enforce`.
- **Limit**: the nonce only helps if no attacker-controlled HTML reaches the
  page; Hologram HTML-escapes template values, and the allow-list above stops
  the plug from blessing unknown inline scripts.
- **Tests**: unit tests for the plug (nonce uniqueness over 200 requests,
  header content, every inline script given the nonce, body otherwise unchanged,
  non-HTML and HEAD, modes, the real first-load page); the browser harness
  records every `securitypolicyviolation` and **fails any browser test that
  sees one** (opt out with `@tag csp: :allow`). Playwright's own
  `waitForFunction` uses in-page `eval`, so the driver polls with
  `page.evaluate` instead.

## Threat model (what E2EE does and does not protect)

**Protects against** a database dump, stolen or old backups (Render/Postgres
snapshots after the plaintext is deleted), a hosting-provider or DB-admin
reading rows, server logs and error trackers, and a SQL-injection-style read:
the server only ever holds ciphertext and key wraps, and never sees a key,
passphrase or plaintext (CLAUDE.md rule).

**Does NOT protect against** whoever controls the *code the server delivers*:
a compromised deployment, a malicious operator or a supply-chain compromise
(npm/Hex) can ship JavaScript that reads the passphrase or the unlocked data in
the browser. This is inherent to browser-delivered E2EE; the CSP, SRI-style
hardening and a small, locally-bundled JS surface reduce but cannot remove it.
The Terms and the setup wizard should say so in plain words.

Also not protected: a user's own unlocked browser profile or device (the
"remember this device" option makes that explicit), a weak passphrase (anyone
holding the database can try passphrases offline, so Argon2id cost and a
12+ character minimum matter), and metadata the server must see (workspace
identity, vault size and update times, login identity via OIDC).

**CSP caveat:** Hologram's runtime needs `'unsafe-eval'` (it runs server
payloads through `new Function`), so the policy is nonce + `'self'` with no
`'unsafe-inline'` for scripts but cannot drop `'unsafe-eval'` until Hologram
changes. That weakens defence-in-depth against XSS (it does not by itself open
an injection point); it is tracked under "Still open".

## Go/no-go and later findings

Go on Hologram: the integer engine matches the Decimal engine (orders,
minimums and month counts exactly; interest within the documented sub-cent
drift), the full dashboard runs in a real browser (~50 browser tests), and the
crypto facade passes published vectors. Findings since the spike:

- **Session:** Hologram runs on the Phoenix session in embedded mode, so the
  existing OIDC `user_id` is readable in `init/3` and commands; pages and any
  component with commands need the `Holo.Auth` middleware (it does not cascade
  from a page to its components' commands).
- **One follow-up action per handler:** `put_action` overwrites the previous
  one. Combine effects into a single action's params.
- **Client performance:** Hologram logs a duration for every function call;
  with logging on, a client re-plan of a long payoff took ~25 s. A quieting
  helper (`assets/js/hologram_quiet.mjs`) brings it to ~1 s. The first chart
  switch after load still takes ~2 s (the simulation runs in the browser).
  Dev-build page bundle: ~624 KB (118 KB gzip) with charts; the crypto facade
  adds ~64 KB to a page that imports it. Production size is unmeasured.
- **Incremental build state can go stale** (see `mix holo.clean` and CLAUDE.md).
- **Module loading:** command names are decoded with `to_existing_atom`, so
  dev preloads app modules at boot (`:preload_modules`); releases already do.
- **Static assets:** stale `.gz` siblings in `priv/static/assets` (left by
  `phx.digest`) are served in preference to fresh files when `Plug.Static`
  gzip is on and can silently serve an old stylesheet.

### Snapshot sync groundwork

The snapshot now also carries `updated_at` (ISO 8601) on `settings`, `payments`
and `retirement_profiles` (debts already had it), additively: no key changed
and `schema_version` stays 1. Sync can use it to tell which copy of a row is
newer. No migration was needed (the columns exist).

### Precision audit: `mix drt.audit_snapshot`

The integer snapshot rounds money to cents and APR / minimum-payment rate /
retirement percentages to 0.01% (see `Storage`). Run the audit against a real
database BEFORE moving a plaintext workspace into the vault, so nothing is
rounded silently:

    mix drt.audit_snapshot                       # the environment's database
    DATABASE_PATH=/path/to/copy.db MIX_ENV=prod mix drt.audit_snapshot
    DATABASE_URL=postgres://... mix drt.audit_snapshot

It honours `DATABASE_URL` / `DATABASE_PATH` like `config/runtime.exs`
(`MIX_ENV=prod` also needs the prod `ENCRYPTION_KEY`, since columns are
decrypted through the Cloak vault). Output is one block per workspace --
rows checked per table, then one line per finding:

    workspace <uuid>: checked debts=7 payments=42 settings=1 retirement_profiles=2
      debts.balance id=<uuid> decimals=3 (would round to 123.46)

and a final verdict line: `no precision loss: ...` (exit 0) or
`PRECISION LOSS: n stored value(s) ...` (exit 1). Only ids, column names,
digit counts and the rounded value are printed -- no names, notes or other
personal data. "Would round" is judged with the very `Engine.Convert` round
trip the snapshot uses, so a value reported here is exactly one the snapshot
would change.

It never writes. It does NOT start the application (that would run
`Ecto.Migrator`, `Boot.run/0` and the `DuePayments.Scheduler`); it starts
only the driver apps, `DebtReliefTracker.Vault` and the repo. SQLite is
opened `mode: :readonly` (SQLite itself rejects writes; a missing file is an
error, not a new empty database) and Postgres with
`default_transaction_read_only=on`; the code only issues `SELECT`s, and a
test compares per-table row checksums and the schema before and after a run.
Opening a WAL-mode SQLite file read-only may create empty `-wal`/`-shm`
sidecar files; the database file itself is untouched. Run it on a copy if you
want to be certain.

## Production rollout (decided 2026-11-01)

Context: the local dev database is play data; real users exist only in the
deployed app (Render, Auth0 OIDC, presumably Postgres). The rollout has to be
safe for them.

**Owner decisions**

- **Shared workspaces:** the owner of a workspace that has other members
  migrates anyway, and **the other members lose access** to that workspace's
  financial data (they keep their own workspaces). Because that is
  irreversible for someone who didn't choose it, the migration screen must
  list who will lose access (display name/email only) and require an explicit
  confirmation; finalizing removes the other `workspace_members`, cancels
  pending invitations, and those members' linked retirement profiles live on
  only inside the owner's vault. Members see their own workspace on next login.
- **Users who never come back:** their plaintext stays on the server (still
  protected by the existing server-side Cloak key, ADR 0005) until they next
  log in; the forced setup wizard runs then. No automatic deletion. Admins get
  a count of unmigrated workspaces (no data).

**Rollout requirements**

1. **Two-step deploy.** Step 1: ship the code with `E2EE` unset. The migration
   only adds two empty tables; `/app` runs in plaintext mode; verify. Step 2:
   set `E2EE=true`. Take a Render database backup before step 2. E2EE is
   irreversible in v1 (no E2EE -> plaintext path). Render/Postgres backups keep
   pre-migration plaintext until they age out; say so in the Terms.
2. **Postgres is the production path.** Every migration and the test suite are
   verified against a throwaway local Postgres as well as SQLite.
3. **Safe plaintext deletion.** The server can read the plaintext until it is
   deleted, and `DuePayments.Scheduler` keeps posting payments for unmigrated
   workspaces. The export returns a digest of the plaintext snapshot; the
   delete command must present it and the server refuses if anything changed
   since (so a payment logged during migration cannot be lost). The browser
   re-downloads and verifies the vault before the delete command is sent.
4. **Login is not unlock.** After OIDC login a returning user unlocks with a
   passphrase, passkey or recovery key (new device, new session). Someone who
   lost every method gets an explicit "start over" path that wipes the vault
   (their data is unrecoverable by design).
5. **New users** after deploy go straight to the setup wizard; no plaintext is
   ever written for them.
6. **Server-side readers of plaintext** (the payment scheduler, CSV export,
   retirement member picker; the former LiveView at `/` is gone -- `/` now
   redirects to `/app`) must be inert for encrypted
   workspaces; auto-logged installments move to the client catch-up.

## Migration server contract (plaintext -> vault)

Code: `DebtReliefTracker.E2EE.Migration`, `Holo.Components.MigrationGate`.
Flow: (1) the owner calls `export`; (2) the browser builds the vault from the
snapshot, creates it (`:create_vault`), re-downloads and verifies it
decrypts and matches; (3) only then it calls `finalize` with the export's
digest. Nothing deletes plaintext automatically, ever.

**API** (all owner only: `workspace.owner_user_id` is re-read from the database;
in no-auth mode the default user is the owner)

- `status(ws)` -> `:plaintext_only | :vault_only | :both | :empty`. Plaintext =
  any debt, payment, activity entry, retirement profile, or a non-default
  settings value (budget set, currency != USD, `margin` mode, onboarding
  dismissed). `:both` = vault created, plaintext not yet finalized.
- `export(ws, user)` -> `{:ok, %{snapshot, digest, members, pending_invitations}}`
  or `{:error, :forbidden | :already_encrypted | :nothing_to_migrate | :too_large}`.
  Allowed in `:plaintext_only` and `:both` (re-export after `:changed`).
  `:too_large` = more activity entries than the snapshot carries.
- `dry_run(ws, user)` -> counts per table, `members_to_remove` (display name,
  email), `pending_invitations`. Changes nothing.
- `finalize(ws, user, digest, opts)` -> `{:ok, %{deleted, removed_members,
  canceled_invitations}} | {:ok, :already_clean} | {:error, :forbidden |
  :no_vault | :changed | :members_present | :busy}`. `opts`:
  `confirm_remove_members: true` (exactly `true`), `compact: false`,
  `before_commit: fun` (test seam, runs inside the transaction).

**Digest.** SHA-256 (lower hex) of `canonical/1` over
`%{"v" => 1, "workspace_id", "snapshot" => Storage.Plain.load/1 (collections
sorted by id), "stamps" => id/inserted_at/updated_at of every debt, payment,
activity entry, retirement profile and settings row, "counts"}`. The canonical
form is a tagged, length-prefixed encoding with map entries sorted by string
key, so it does not rely on Jason or map/query ordering; unknown term types
raise. Any added, removed or edited row changes it. It is bound to the
workspace id.

**finalize, in order, in ONE transaction:** lock (below) -> owner re-check
(`:forbidden`) -> vault must exist (`:no_vault`, nothing is ever deleted
without an uploaded vault) -> nothing left means `:already_clean` -> recompute
the digest under the locks, constant-time compare (`:changed`) -> other
members/invitations need `confirm_remove_members: true` (`:members_present`) ->
delete activity logs, payments, debts, retirement profiles (this workspace
only), reset the settings row to defaults (row kept; `monthly_budget_enc`
NULL), delete the other `workspace_members` and all pending invitations.
The workspace, owner, owner membership, account rows, the vault and its wraps
are never touched. Any exception rolls everything back.

**Locks.** PostgreSQL: `lock_timeout 10s`, then `SELECT ... FOR UPDATE` on the
workspace, then its debts, payments, retirement profiles and settings rows,
before the digest is recomputed. `FOR UPDATE` conflicts with the `FOR KEY SHARE`
that foreign-key checks take, so a concurrent payment/debt/activity insert
waits and then fails its FK or is part of the digest; a deadlock with a
concurrent `Payments.log_payment` (insert-then-update order) aborts one side
and finalize reports `{:error, :busy}` (nothing deleted; retry). Two racing
finalizes serialize on the workspace row: one deletes, the other gets
`:already_clean`. SQLite: single writer; a no-op write on the workspace row
takes the write lock first. Under heavy SQLite contention a loser can time out
(`:busy`); everything rolled back.

**Scheduler.** `DuePayments.Scheduler` skips every workspace that has a vault
(including `:both`), so it cannot add plaintext after the export. A payment
posted in the window anyway (the dashboard, API) changes the digest.

**What stays behind.** SQLite: a best-effort `VACUUM` + `wal_checkpoint(TRUNCATE)`
runs after the commit (never inside), and a test shows the plaintext column
bytes are gone from the database file and WAL. PostgreSQL: nothing more can be
done server-side: old backups, WAL archives and replicas keep the plaintext
until they age out (say so in the Terms). Users who never return keep their
Cloak-encrypted plaintext; admins see counts only (`/admin` Users tab).

**Failure modes.** `:changed` -> re-export, merge into the vault, re-verify,
finalize again. `:busy`/`:failed` -> nothing deleted, retry. A crash after the
vault is created and before finalize leaves `:both`: harmless, the user
resumes. Finalize is idempotent.

**Client flow** (`Holo.MigrationFlow`, pure state machine, effects as data):

    :checking -> :needs_migration -> [:confirming_members] -> :setting_up
      -> :verifying -> :finalizing -> :done
    :finalizing --:changed--> :re_exporting -> :setting_up (rebuild vault via CAS) -> :verifying
    :finalizing --:busy--> retry with backoff 1 s / 3 s / 9 s, then :failed(:busy)
    status :both (reload mid-flow) -> re-export -> :verifying (stale vault: :rebuild)

`:finalizing` is reachable ONLY from `:verifying` after `verify(export_snapshot,
VaultDoc.view(re-downloaded doc))` is `:ok`: same ids and counts, every field
equal, order-insensitive; only `updated_at`/`inserted_at` (restamped) and
atom-vs-string keys are normalised. The finalize digest is the verified
export's. Other members are removed only after an explicit `true`
confirmation. Tests: `test/debt_relief_tracker_web/holo/migration_flow_test.exs`
(including a seeded random-event property test).

**Commands** (`MigrationGate`, workspace/user from the session only; export and
finalize use a strict per-workspace bucket, 8 burst then 1 per 15 s; one page
action each, `target: "page"`):

| command | params | page action | reply |
|---|---|---|---|
| `:migration_status` | none | `:migration_status_result` | `%{ok, status, owner}` |
| `:migration_export` | none | `:migration_export_result` | `%{ok, snapshot, digest, members, pending_invitations}` |
| `:migration_dry_run` | none | `:migration_dry_run_result` | `%{ok, counts, members_to_remove, pending_invitations}` |
| `:migration_finalize` | `%{digest, confirm_remove_members, vault_rev, vault_blob_sha256}` | `:migration_finalize_result` | `%{ok, deleted, removed_members, canceled_invitations}` or `%{ok, already_clean}` |

Errors are `%{ok: false, error: atom}` (the atoms above plus `:rate_limited`,
`:invalid`, `:failed`). The component is not yet mounted in `DashboardPage`.

`vault_rev` / `vault_blob_sha256` (lower-hex SHA-256 of the blob string) name the
vault the browser downloaded and verified. Inside the finalize transaction, with
the vault row locked, the server compares them with the stored vault and
answers `:vault_changed` (nothing deleted) on any difference, so a vault that
was overwritten, rebuilt or rolled back after verification cannot authorise the
deletion. The browser then re-downloads and re-verifies (bounded), rebuilding
if the new vault does not match.

### Known limits

- A concurrent plaintext insert that was waiting on the workspace lock can land
  after finalize commits (Postgres FK key-share lock on the workspace row). The
  status then returns to `:both` and the migration screen offers to migrate the
  stray rows. The scheduler and E2EE mode make this practically unreachable.

## Vault document, ledger and merge

Code: `DebtReliefTracker.VaultDoc` (+ `.Ledger`, `.Merge`, `.Json`, `.Check`,
`.Shape`, `.Stamp`), `assets/js/vault_json_facade.mjs`. (`VaultDoc`, not
`Vault`: that name is the Cloak module.) All pure and client-safe: the browser
applies every change to the decrypted document, merges on conflict and
re-encrypts; the server never runs any of it for an E2EE workspace.

**Document** (`schema_version` 1, one JSON text per vault, encrypted as the
`rev`-bound blob): `settings` + `settings_updated_at` (one stamp per key, so
settings merge per key), and four maps keyed by record id: `debts`,
`payments`, `activity`, `retirement_profiles`. Every record has `id`,
`updated_at` and `deleted` (tombstone); records otherwise use the `Storage`
snapshot keys and units, plus bookkeeping the UI never sees: debts carry
`inserted_at` and `applied`, the others `inserted_at`. `VaultDoc.view/1` is a
plain `Storage.snapshot` of the live records in `Snapshot.build`'s order, so
the existing components work unchanged (a payment is live iff its debt is; an
activity entry of a deleted debt shows `debt_id: nil`, like the FK's SET NULL;
displayed balances are clamped at 0). `VaultDoc.from_snapshot/2` is the
plaintext -> vault migration step (no tombstones; each debt's `applied` is all
its payments; debts get a synthetic `inserted_at` that preserves list order).
`decode/1` is strict (types, sizes, unknown `schema_version` -> `:invalid`).
Stamps are `YYYY-MM-DDTHH:MM:SS.ffffffZ`, so string order is time order.

**Ledger** (`apply_change(doc, change, ctx)`, `catch_up(doc, ctx)`): every
change of the `Storage` vocabulary, with `Storage.Plain`'s error maps and
activity entries. The caller supplies `ctx = %{now, today, new_id, actor,
members}` (no clock/UUIDs in pure code). It is atomic, total (bad input ->
`{:invalid, ...}`), and keeps `updated_at` strictly increasing per record.
Parity with Plain is tested after every step of scripted and seeded random
sequences (`test/debt_relief_tracker/vault_doc/parity*_test.exs`). Known
divergences: non-integer numerics are `"is invalid"` (Ecto casts `"30"`);
`reconcile_balance` works in whole cents (Plain's activity `"amount"` keeps
extra decimals when an interest estimate is involved, and Decimal rounding can
leave a balance 1e-24 below the cent figure, which makes Plain reject a later
payment of exactly that balance); the document is edited atomically.

**Auto-posted payments have deterministic ids**: `Engine.DueSchedule.payment_id`
(`"<debt id>:<yyyy-mm-dd>"`) for the payment, `"<payment id>:logged"` for its
activity entry, `"<debt id>:<date>:skipped"` for a skip. `catch_up` (on open,
both modes) posts every missed cycle of `automatic` debts (confirm debts are
only reported) and is idempotent; two devices catching up create the same
records and the merge dedupes them. If a payment already exists (arrived via a
merge) the cycle is only stamped handled.

**Merge** (`Merge.merge(a, b)`: commutative, associative, idempotent; property
tested with seeded random op sequences on 3-4 replicas). Payments and activity
are a union by id; a payment is deleted iff its debt is (so a tombstone beats a
live copy, and a debt resurrected by a strictly newer edit brings its payments
back). Debts and retirement profiles are per-record last-writer-wins on
`updated_at`; equal stamps: tombstone wins, then the greater JSON of the
deliberate content. Settings: per key.

*Concurrent payments.* Balances are baselines, never recomputed from payments,
yet two devices that each log a payment must both reduce the balance. Each debt
carries `applied: %{payment_id => principal}` = exactly what its `balance`
already reflects. Logging a payment subtracts the principal and records it in
`applied` but does **not** bump `updated_at` (so it never loses the LWW race
against a concurrent rename). Editing the balance directly is a new baseline
(`applied` := all payments the document has). Merging takes the LWW winner as
the baseline and applies every payment of the union it has not applied, once:
`balance = winner.balance - sum(principal(p) - winner.applied[p])`. Equivalent
statement: `gross = balance + sum(applied)` is merge-invariant and the result
is `gross(winner) - sum(principal over the union)`, independent of merge order;
the winner is chosen from the deliberate content only (everything but
`balance`, `applied`, `last_due_handled_on`), so intermediate merges do not
change who wins. `last_due_handled_on` merges as the max. A payment concurrent
with a baseline edit lowers the new baseline (documented, deliberate). Two
devices over-paying the same debt can push the stored balance below 0 (kept
exact for associativity; the view clamps).

**JSON.** Jason is not in the browser. `VaultDoc.Json` is a pure Elixir
reference codec (deterministic: sorted keys, no whitespace, integers only
within +-(2^53-1), strict bounded decoder: depth <= 64, strings <= 1 MiB, input
<= 16 MiB, rejects floats/duplicate keys/bad escapes) used on the server and by
ExUnit. Hologram's interpreter copies lists/maps on every cons/`Map.put` and
costs ~100 us per call, so the pure decoder takes ~13 s for 900 records; in the
browser `encode/decode` therefore delegate to a ~200-line generic facade
(`vault_json_facade.mjs`, same grammar and limits, no app logic) and fall back
to the pure code where JS interop is a no-op. `JSON.parse/stringify` were not
used directly (key order, doubles above 2^53, duplicate keys, unbounded). The
browser test runs a fixed script of every change kind, a merge and a catch-up
through the **compiled** modules and asserts the resulting JSON equals ExUnit's
byte for byte, and that facade and pure codecs agree on tricky data. Measured
in headless Chromium on a document of 1200 payments + 2400 activity entries +
12 debts (~600 KB): encode 70 ms, decode 1.5 s, view 0.8 s, log a payment 0.4 s,
self-merge 3.8 s, catch-up 0.1 s. Code reachable from the browser avoids
`Enum.filter/reject/any?/join/with_index`, `String.codepoints` on long strings
and reduce-with-`Map.put` for the same reason (use `for`, `:lists.*`, `Map.new`,
`Map.merge/3`, `IO.iodata_to_binary`).

## Hardening: stalled saves, clock skew, rollback record

- **Unreadable conflict reply.** If the server's copy cannot be decrypted or
  decoded during a save conflict (a newer app version wrote it, or it is
  damaged), `SaveLoop.stalled/1` releases the in-flight flag, keeps the local
  doc dirty and sets `:failed`. The bar says the server copy could not be read
  and offers "Retry save" (a new save conflicts again, i.e. re-fetches). Lock
  is no longer blocked forever; "lock anyway" remains the explicit discard.
- **Clock skew (last-writer-wins trusts wall clocks).** Every `VaultGate` reply
  carries an additive `server_now` (ISO, not secret). The client keeps the
  offset to its own clock and derives an estimate of server time. Rule:
  * Stamping (`Ledger`): `stamp = min(device_now, server_now + 5 min)`, and
    never earlier than the newest stamp already in the document (monotonic).
    Stamps already more than 24 h ahead of `server_now` are ignored as "newest".
  * Merging (`Merge.merge/3`, `server_now:`): an incoming `updated_at` more than
    24 h ahead of `server_now` is suspect and compared as `server_now` (and
    loses a tie to a genuine stamp). Stored stamps are not rewritten.
  Without a server reference (no reply yet) behaviour is as before.
- **Rollback record.** The IndexedDB last-seen `{rev, hash}` is monotonic:
  `seenRecord` never lowers it; only `seenAcknowledge` (the user's explicit
  "continue" after a rollback warning, or creating a new vault) does, and acks
  are counted in `vault.rollback_acks`. If IndexedDB is unavailable the check
  proceeds but a non-blocking banner says rollback protection is off.
